# vehicleService.js Documentation

## 1. File Overview

**File:** `vehicleService(20260826-120444).js`

This service provides the vehicle-management and vehicle-analytics
business logic for the SEWAC system.

It handles:

``` text
Vehicle directory retrieval
Live vehicle status calculation
Vehicle worked-today detection
Vehicle lookup by ID
Vehicle creation
Vehicle updates
Vehicle deletion
Vehicle KPI summary
Average waste generated by zone
Master Citizen geographic hierarchy resolution
Daily telemetry-table resolution
Telemetry weight aggregation
```

The service combines three database layers:

``` text
mainDb
    ↓
vehicle_master

masterCitizenPrisma
    ↓
City / Zone hierarchy

telemetryDb
    ↓
day_DDMMYYYY
    ↓
vehicle telemetry tables
```

The major analytical flow is:

``` text
Registered Vehicles
        ↓
Vehicle Telemetry Tables
        ↓
Latest Telemetry
        ↓
30-Minute Activity Threshold
        ↓
ACTIVE / INACTIVE

Registered Vehicles
        +
Today's Telemetry
        ↓
Worked Today

Master Citizen Zones
        +
vehicle_master
        +
Daily Telemetry
        ↓
Zone Waste Aggregation
        ↓
Average Waste
```

# 3. DATABASE IDENTIFIER SAFETY

The service defines:

``` js
IDENTIFIER_REGEX
```

using:

``` text
/^[A-Za-z_][A-Za-z0-9_]*$/
```

This validates dynamically selected PostgreSQL identifiers.

A valid identifier must:

``` text
Start with a letter or underscore
Continue with letters, numbers, or underscores
```

------------------------------------------------------------------------

# 4. quoteIdentifier()

This helper validates and quotes a dynamic database identifier.

It receives:

``` text
identifier
```

If the value is not a string or does not match:

``` text
IDENTIFIER_REGEX
```

the service throws:

``` text
Unsafe database identifier: <identifier>
```

For a valid identifier, it returns a quoted PostgreSQL identifier.

Example:

``` text
vehicle_table
        ↓
"vehicle_table"
```

This helper is used whenever the service dynamically interpolates:

``` text
Day tables
Vehicle telemetry tables
City dynamic tables
```

# 10. Missing Daily Telemetry Table

If PostgreSQL returns:

``` text
42P01
```

the service interprets the error as:

``` text

```

It logs a warning and returns:

``` text

```

This means a missing day table does not break vehicle analytics.

------------------------------------------------------------------------

# 11. getVehiclesWorkedToday()

This function determines whether each vehicle has actually worked on the
selected date.

It receives:

``` text
todayVehicleTables
selectedDate
```

A vehicle is considered to have worked when at least one telemetry
record has a positive value in any of:

``` text
wetweight
dryweight
otherweight
```

------------------------------------------------------------------------

# 12. Worked-Today Definition

The function checks:

``` text
iottimestamp >= selectedDate
```

and:

``` text
iottimestamp < selectedDate + 1 day
```

Therefore only telemetry belonging to the selected calendar date is
considered.

------------------------------------------------------------------------

# 13. Positive Weight Condition

A vehicle is considered to have worked when:

``` text
COALESCE(wetweight, 0) > 0
```

or:

``` text
COALESCE(dryweight, 0) > 0
```

or:

``` text
COALESCE(otherweight, 0) > 0
```

Therefore:

``` text
Any positive waste weight
        ↓
workedToday = true
```

------------------------------------------------------------------------


# 51. Midnight Boundary Handling

Yesterday's telemetry is intentionally included because a vehicle can
have a recent packet just before midnight.

Example:

``` text
Yesterday:
23:58

Today:
00:10
```

The difference is:

``` text
12 minutes
```

Therefore the vehicle should still be:

``` text
ACTIVE
```

The combination of today's and yesterday's telemetry prevents the
date-table boundary from incorrectly marking the vehicle inactive.

# 54. Latest Packet Per Vehicle

For every unique telemetry table, the service queries:

``` text

```

``` text

```

This provides the latest received telemetry timestamp for each vehicle
in that table.

------------------------------------------------------------------------

# 55. Important Timestamp Rule

For:

``` text
getVehicleSummary()
```

the live-status calculation uses:

``` text
receivedtimestamp
```

not:

``` text
iottimestamp
```

This is an important distinction from other telemetry functionality in
the project.

The status calculation therefore represents:

``` text
Latest packet received by the system
```

rather than:

``` text
Latest IoT event timestamp
```

------------------------------------------------------------------------

# 56. Registered Vehicle Restriction

Telemetry is only considered when its:

``` text
vehiclenumber
```

matches a vehicle in:

``` text
registeredVehicles
```

Unregistered telemetry vehicles are ignored.

------------------------------------------------------------------------

# 57. Multiple Telemetry Tables

A registered vehicle can appear in multiple telemetry tables.

The service keeps the newest:

``` text
lastReceivedTimestamp
```

across all inspected tables.

The lookup is:

``` text

```

------------------------------------------------------------------------

# 58. Invalid Telemetry Timestamp

If:

``` text
lastReceivedTimestamp
```

cannot be converted into a valid JavaScript date, the record is ignored.

------------------------------------------------------------------------



# 60. Active Vehicle

If the vehicle has a latest telemetry timestamp, the service checks:




# 61. Inactive Vehicle

If the latest telemetry timestamp is older than:

``` text

```

``` text

```

``` text
Static vehicle_master.status
```

``` text
Live telemetry status
```

``` text
ACTIVE
```

``` text
latest received telemetry
>=
current time - 30 minutes
```

``` text
INACTIVE
```

# 101. Worked-Today Architecture

The service introduces a separate concept:

``` text
workedToday
```

This is not the same as:

``` text
status
```

A vehicle can therefore conceptually be:

``` text
workedToday = true
status = INACTIVE
```

For example:

``` text
Vehicle recorded positive waste at 09:00
        ↓
workedToday = true

Current time = 18:00
        ↓
Latest telemetry older than 30 min
        ↓
status = INACTIVE
```

This allows the directory to show both:

``` text
Whether the vehicle worked today
```

and:

``` text
Whether it is currently live
```

# 102. Telemetry Timestamp Distinction

The service uses two different timestamp fields for different purposes.

## Live Vehicle Status

Uses:

``` text
receivedtimestamp
```

to determine when the system last received a packet.

## Worked Today

Uses:

``` text
iottimestamp
```

to determine whether positive waste was recorded on the selected date.

## Zone Waste Aggregation

Uses:

``` text
iottimestamp
```

to determine whether weight belongs to the selected calendar date.

# 114. Important Implementation Detail

`workedToday` is calculated independently from live status.

The logic is based on:

``` text

OR
Positive dryweight
OR

```


even when:


The zone average is:

# 118. Summary

`vehicleService(20260826-120444).js` is the central vehicle
business-logic service for SEWAC.

It manages:

``` text
Vehicle CRUD
Vehicle directory
Live vehicle status
Worked-today indicator
Vehicle KPI summary
Zone-wise waste aggregation
```

The live status architecture is:

``` text
Registered Vehicle
      ↓
Today + Yesterday Telemetry
      ↓
MAX(receivedtimestamp)
      ↓
Within 30 minutes?
      ↓
ACTIVE / INACTIVE
```

The worked-today architecture is:

``` text
Today's Telemetry
      ↓
Positive wetweight?
OR positive dryweight?
OR positive otherweight?
      ↓
workedToday
```

The zone waste architecture is:

``` text
Master Citizen Official Zones
      ↓
Registered Vehicles
      ↓
Daily Telemetry
      ↓
Wet + Dry + Other Weight
      ↓
Zone Waste
      ↓
Total Waste
      ↓
Average Across All Zones
```

The core waste formula is:

``` text
Total Vehicle Waste (kg)
=
Wet Weight
+
Dry Weight
+
Other Weight
```

and the zone-level average is:

``` text
Average Waste Generated
=
Total Waste Generated
÷
Number of Registered Zones
```

The service therefore provides the backend logic needed for:

``` text
Vehicle Directory
Vehicle Status
Worked Today
Vehicle KPIs
Zone Waste Graph
Average Waste KPI
Vehicle CRUD
```

while keeping static vehicle-master information separate from dynamic
telemetry-derived operational status.
