# SEWAC Telemetry Database Initialization

This README explains the initialization process for the SEWAC Telemetry Database.

The initialization module is responsible for preparing the telemetry database with the foundational tables, columns, and indexes required by the telemetry processing system.

This file does **not** handle the creation of individual vehicle telemetry tables, day tables, week tables, month tables, year tables, or heartbeat tables.

Instead, it prepares the core database structures required before the telemetry pipeline begins processing data.

# 2. Purpose of Initialization

The telemetry database requires a small set of foundational structures before the rest of the telemetry system can operate correctly.

When initialization runs, it performs the following operations:

    1. Create the vehicle cumulative table
    2. Add the master telemetry processing status column
    3. Add the master telemetry cumulative weight column
    4. Create the master telemetry processing index

The complete initialization flow is:

    Telemetry Application Starts
            |
            v
    InitializeTelemetryDB.initialize()
            |
            +--> vehicle_cumulative
            |
            +--> processing_status
            |
            +--> cumulativeWeight
            |
            +--> telemetry status index
            |
            v
    Telemetry Database Ready

# 6. initialize()

The initialization process starts with:

    async initialize() {
      console.log("Initializing Telemetry Database...");

The method is asynchronous because database operations are asynchronous.

Each SQL statement is executed using `await`.

This ensures that the initialization process waits for each database operation to complete before continuing.

The general flow is:

    initialize()
        |
        v
    Execute SQL
        |
        v
    Wait for completion
        |
        v
    Execute next SQL
        |
        v
    Database Ready

---

# 7. Vehicle Cumulative Table

The first database operation is:

    await telemetryDb.$executeRawUnsafe(
      queries.createVehicleCumulativeTable()
    );

This executes the SQL generated by:

    createVehicleCumulativeTable()

The SQL creates:

    vehicle_cumulative

The table stores the running cumulative waste weight for each vehicle.

Conceptually:

    vehicle_cumulative
            |
            +--> vehicle_number
            |
            +--> cumulative_weight
            |
            +--> updated_at

The initialization step ensures this table exists before telemetry processing begins.

The table is important because vehicle cumulative weight can be updated continuously as telemetry records are processed.

---

# 8. Why Vehicle Cumulative Is Initialized First

The vehicle cumulative table is a foundational structure used by telemetry processing.

The processing flow can eventually become:

    Telemetry
        |
        v
    Vehicle identified
        |
        v
    Calculate / receive weight
        |
        v
    Update vehicle_cumulative
        |
        v
    Running vehicle total

Creating this table during initialization guarantees that the cumulative-weight operation has a destination before the telemetry pipeline starts processing records.

---

# 9. Master Telemetry Processing Status

The second operation is:

    await telemetryDb.$executeRawUnsafe(
      queries.addMasterTelemetryStatusColumn()
    );

This executes:

    addMasterTelemetryStatusColumn()

The SQL adds the following column to `master_telemetry`:

    processing_status VARCHAR(20)
    DEFAULT 'COMPLETED'

The column is created using:

    ADD COLUMN IF NOT EXISTS

This is important because initialization may run against a database where the column already exists.

Instead of failing, PostgreSQL simply leaves the existing column unchanged.

---

# 10. Purpose of processing_status

The `processing_status` field is used to track the state of telemetry records inside the master telemetry buffer.

The processing lifecycle is:

    Incoming Telemetry
            |
            v
        PROCESSING
            |
        +---+---+
        |       |
        v       v
    COMPLETED  FAILED

This allows the telemetry pipeline to distinguish between:

- Records currently being processed
- Records successfully processed
- Records that failed processing

The initialization module therefore prepares the database for the telemetry processing lifecycle.

---

# 11. Master Telemetry Cumulative Weight

The third operation is:

    await telemetryDb.$executeRawUnsafe(
      queries.addMasterTelemetryCumulativeColumn()
    );

This executes:

    addMasterTelemetryCumulativeColumn()

The SQL ensures that `master_telemetry` contains:

    "cumulativeWeight" DECIMAL(10,2)

The column is also added using:

    ADD COLUMN IF NOT EXISTS

Therefore, if the database already contains the column, nothing is changed.

---

# 12. Why IF NOT EXISTS Is Important

The initialization process may run more than once.

For example:

    Application Start
        |
        v
    Initialize Database
        |
        v
    Application Restart
        |
        v
    Initialize Database Again

Without `IF NOT EXISTS`, the second initialization could fail because the column or table already exists.

Using:

    IF NOT EXISTS

makes the initialization operation safe to repeat.

This gives the initialization process an idempotent-like behaviour for these schema operations.

---

# 13. Master Telemetry Status Index

The fourth operation is:

    await telemetryDb.$executeRawUnsafe(
      queries.createMasterTelemetryStatusIndex()
    );

This executes:

    createMasterTelemetryStatusIndex()

The SQL creates the index:

    idx_master_telemetry_status_received

on:

    processing_status
    "receivedTimestamp"

The index is created using:

    CREATE INDEX IF NOT EXISTS

Again, this allows the initialization process to safely run when the index already exists.

---

# 14. Why the Index Is Important

The telemetry pipeline frequently needs to work with records based on their processing status and reception time.

For example, the system may need to locate records that are:

    processing_status = 'PROCESSING'

or:

    processing_status = 'COMPLETED'

while also considering:

    receivedTimestamp

The index:

    processing_status
    +
    receivedTimestamp

helps PostgreSQL efficiently locate records for these operations.

Conceptually:

    master_telemetry
            |
            v
    processing_status
            +
    receivedTimestamp
            |
            v
    Indexed Lookup
            |
            v
    Telemetry Processing

---

It is important to understand that `initializeTelemetryDB.js` does not create every telemetry table.

It only prepares the foundational database structures.

It does **not** directly create:

    Day tables
    Vehicle telemetry tables

            |

# 17. Initialization vs Dynamic Table Management

There are two different responsibilities in the telemetry architecture.

## Database Initialization

Handled by:

    src/telemetry/initialize/initializeTelemetryDB.js

Responsible for:

- `vehicle_cumulative`
- `processing_status`
- `cumulativeWeight`
- Master telemetry index

---

## Dynamic Table Management

Handled by the telemetry manager layer.

Responsible for dynamically managing:

- Year tables
- Month tables
- Week tables
- Day tables
- Vehicle telemetry tables
- Vehicle heartbeat tables
- Table relationships

This distinction is important when understanding the overall architecture.

# 19. Complete File

The complete initialization file is:

    const telemetryDb = require("../../config/telemetryDb");
    const queries = require("../queries/query");

    class InitializeTelemetryDB {
      async initialize() {
        console.log("Initializing Telemetry Database...");

        await telemetryDb.$executeRawUnsafe(
          queries.createVehicleCumulativeTable()
        );

        await telemetryDb.$executeRawUnsafe(
          queries.addMasterTelemetryStatusColumn()
        );

        await telemetryDb.$executeRawUnsafe(
          queries.addMasterTelemetryCumulativeColumn()
        );

        await telemetryDb.$executeRawUnsafe(
          queries.createMasterTelemetryStatusIndex()
        );

        console.log("Telemetry Database Initialized Successfully.");
      }
    }

    module.exports = new InitializeTelemetryDB();
