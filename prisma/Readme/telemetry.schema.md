# SEWAC Telemetry Database Schema

This README explains the database schema used by the **SEWAC Telemetry System**.

The telemetry database stores data received from IoT and field devices during waste-collection operations. It contains information related to collection events, citizens, RFID tags, waste quantities, GPS locations, vehicles, drivers, IoT devices, errors, and operational actions.

---

## 1. Prisma Client Configuration

The telemetry database uses a dedicated Prisma Client:

    generator telemetryClient {
      provider = "prisma-client-js"
      output   = "../generated/telemetry"
    }

### Provider

    prisma-client-js

This tells Prisma to generate a JavaScript/Node.js client that can be used by the SEWAC backend to communicate with the telemetry database.

### Output

    ../generated/telemetry

The generated client is stored separately from the other Prisma clients in the project.

This separation is important because SEWAC works with multiple databases and different data domains. Telemetry-related services therefore use their own generated Prisma client.

---

# 2. Database Configuration

    datasource db {
      provider = "postgresql"
      url      = env("TELEMETRY_DATABASE_URL")
    }

The telemetry database uses **PostgreSQL**.

The database connection URL is loaded through the environment variable:

    TELEMETRY_DATABASE_URL

Database credentials and connection details are not hard-coded into the source code.

The connection flow is:

    SEWAC Backend
          |
          v
    TELEMETRY_DATABASE_URL
          |
          v
    PostgreSQL Telemetry Database

This allows different telemetry databases to be used for different environments such as development, testing, staging, and production.

---

# 3. MasterTelemetry Model

The central model in the telemetry schema is:

    model MasterTelemetry {

`MasterTelemetry` represents the master collection of telemetry records received from SEWAC's IoT and field systems.

A telemetry record can contain information about:

- When the event occurred
- When the event was received
- RFID identification
- Citizen identification
- Waste type
- GPS location
- Waste weights
- Driver
- Vehicle
- IoT unit
- Firmware version
- Collection type
- Remarks
- Error information
- Citizen contact
- Driver actions

Most fields are optional because telemetry packets may not always contain every available value.

---

# 4. Primary Identifier

    id BigInt @id @default(autoincrement())

The `id` field uniquely identifies every telemetry record.

### BigInt

`BigInt` is used because telemetry systems can generate a very large number of records over time.

### @id

Marks `id` as the primary key.

### @default(autoincrement())

Automatically generates a unique identifier when a new telemetry record is inserted.

---

# 5. Timestamp Information

## IoT Timestamp

    iotTimestamp DateTime?

This stores the timestamp generated by the IoT device.

It represents the time at which the device reports that the telemetry event occurred.

The field is optional because an IoT device may not always provide a valid timestamp.

---

## Received Timestamp

    receivedTimestamp DateTime @default(now())

This stores the time at which the SEWAC system receives the telemetry data.

Unlike `iotTimestamp`, this field is required and receives the current time automatically when the record is created.

The distinction is:

    IoT Device
        |
        | Event occurs
        v
    iotTimestamp
        |
        | Network / processing delay
        v
    SEWAC Backend
        |
        v
    receivedTimestamp

This distinction is useful when investigating:

- Network delays
- Offline devices
- Delayed telemetry packets
- Connectivity problems
- Device clock issues
- Synchronization problems

---

## Created At

    createdAt DateTime @default(now())

This records when the database record was created.

The telemetry system therefore maintains three useful time references:

| Field | Meaning |
|---|---|
| `iotTimestamp` | Time reported by the IoT device |
| `receivedTimestamp` | Time the backend received the telemetry |
| `createdAt` | Time the database record was created |

These timestamps should not be treated as interchangeable.

---

# 6. RFID Information

## RFID EPC

    rfidEpc String?

Stores the RFID Electronic Product Code associated with the collection event.

The RFID value can be used to identify the RFID tag involved in the collection process.

This field is optional because not every telemetry event necessarily contains RFID information.

---

# 7. Citizen Information

## Citizen ID

    citizenId Int?

Stores the SEWAC citizen identifier associated with the telemetry record.

This allows telemetry data to be connected back to a citizen's collection activity.

Conceptually:

    Telemetry Event
          |
          v
      citizenId
          |
          v
    Citizen Information

---

## Citizen Contact

    citizenContact String?

Stores the citizen contact information associated with the event when available.

This field is optional because not every telemetry event contains citizen contact information.

---

# 8. Waste Information

## Waste Type

    wasteType String?

Stores the type or category of waste associated with the collection event.

The actual values used by the system are determined by the SEWAC application and telemetry-processing logic.

---

## Wet Weight

    wetWeight Decimal? @db.Decimal(10,2)

Stores the measured wet-waste weight.

The value is stored using `Decimal(10,2)`, allowing two digits after the decimal point.

---

## Dry Weight

    dryWeight Decimal? @db.Decimal(10,2)

Stores the measured dry-waste weight.

---

## Other Weight

    otherWeight Decimal? @db.Decimal(10,2)

Stores the measured weight belonging to other waste categories.

---

## Cumulative Weight

    cumulativeWeight Decimal? @db.Decimal(10,2)

Stores the cumulative weight associated with the telemetry event.

The separate weight fields allow SEWAC to retain detailed waste information instead of storing only one total.

Conceptually:

    Wet Weight
        |
    Dry Weight
        |
    Other Weight
        |
        v
    Waste Collection Information
        |
        v
    Cumulative Weight

The weight information can later be used for:

- Waste analytics
- Collection statistics
- Ward-level analysis
- Vehicle-level analysis
- Historical reporting
- Operational monitoring

---

# 9. GPS Location

## Latitude

    latitude Decimal? @db.Decimal(10,7)

Stores the latitude associated with the telemetry event.

The coordinate is stored with seven decimal places of precision.

---

## Longitude

    longitude Decimal? @db.Decimal(10,7)

Stores the longitude associated with the telemetry event.

Together, latitude and longitude represent the geographical location of the collection event:

    latitude
        +
    longitude
        |
        v
    Collection Location

This information can be used for:

- Collection tracking
- Vehicle monitoring
- Route analysis
- Map visualization
- Ward-level analysis
- Operational reporting

---

# 10. Driver Information

## Driver Name

    driverName String?

Stores the driver associated with the collection event.

This allows telemetry records to be connected with the driver responsible for the collection operation.

The operational relationship can be understood as:

    Telemetry Event
          |
          v
        Vehicle
          |
          v
        Driver
          |
          v
    Collection Operation

---

# 11. Vehicle Information

## Vehicle Number

    vehicleNumber String?

Stores the vehicle registration number or vehicle identifier associated with the telemetry event.

This allows telemetry data to be grouped and analysed by vehicle.

Potential uses include:

- Vehicle monitoring
- Collection history
- Route analysis
- Vehicle performance analysis
- Operational reporting

---

# 12. IoT Device Information

## Firmware Version

    firmwareVersion String?

Stores the firmware version reported by the IoT device.

This is useful when diagnosing telemetry problems and identifying whether an issue is associated with a particular firmware version.

It can help with:

- Device troubleshooting
- Firmware monitoring
- Device comparison
- Historical debugging

---

## Unit Number

    unitNumber String?

Stores the identifier of the IoT/telemetry unit that generated the record.

This allows a telemetry record to be traced back to the specific field device that generated it.

Conceptually:

    Unit Number
         |
         v
    IoT Device
         |
         v
    Telemetry
         |
         v
    Collection Event

---

# 13. Collection Information

## Collection Type

    collectionType String?

Stores the type of collection associated with the telemetry event.

The actual collection types are controlled by the SEWAC application and telemetry-processing logic.

---

## Remarks

    remarks String?

Stores additional information associated with the telemetry or collection event.

This provides a flexible field for information that does not fit into the structured telemetry fields.

---

# 14. Error Information

## Error Code

    errorCode String?

Stores an error code associated with the telemetry event.

This allows telemetry records containing errors to remain available for investigation and diagnostics.

A simplified processing flow is:

    Telemetry Received
           |
           v
    Check Error Code
           |
       +---+---+
       |       |
       v       v
     Error   No Error
       |       |
       v       v
    Diagnostic Normal
      Analysis Processing

The exact meaning of each error code depends on the IoT device and the SEWAC telemetry-processing logic.

---

# 15. Driver Action

    driverAction String?

Stores an action or operational state associated with the driver during the collection event.

This provides additional operational context for understanding a telemetry record.

---

# 16. Database Table Mapping

The schema contains:

    @@map("master_telemetry")

The Prisma model is named:

    MasterTelemetry

while the corresponding PostgreSQL table is named:

    master_telemetry

Therefore:

    Prisma Model
    MasterTelemetry
          |
          v
    PostgreSQL Table
    master_telemetry

The `@@map` directive allows the application to use the Prisma model name while keeping the required PostgreSQL table name.

---

# 17. Complete Prisma Schema

    generator telemetryClient {
      provider = "prisma-client-js"
      output   = "../generated/telemetry"
    }

    datasource db {
      provider = "postgresql"
      url      = env("TELEMETRY_DATABASE_URL")
    }

    model MasterTelemetry {
      id                   BigInt      @id @default(autoincrement())
      iotTimestamp         DateTime?
      receivedTimestamp    DateTime    @default(now())
      rfidEpc              String?
      citizenId            Int?
      wasteType            String?
      latitude             Decimal?    @db.Decimal(10,7)
      longitude            Decimal?    @db.Decimal(10,7)
      wetWeight            Decimal?    @db.Decimal(10,2)
      dryWeight             Decimal?    @db.Decimal(10,2)
      otherWeight           Decimal?    @db.Decimal(10,2)
      cumulativeWeight      Decimal?    @db.Decimal(10,2)
      driverName            String?
      vehicleNumber         String?
      firmwareVersion       String?
      unitNumber            String?
      collectionType        String?
      remarks               String?
      errorCode             String?
      citizenContact        String?
      driverAction          String?
      createdAt             DateTime    @default(now())

      @@map("master_telemetry")
    }

# 18. Overall Telemetry Data Flow

At a high level, telemetry data flows through SEWAC as follows:

    IoT / Field Device
            |
            v
    Telemetry Packet
            |
            v
    SEWAC Telemetry Processing
            |
            v
    MasterTelemetry
            |
            v
    master_telemetry
            |
            v
    Telemetry Query Layer
            |
            +-------------------+
            |                   |
            v                   v
        Analytics          Operational
                           Applications

The `master_telemetry` table acts as the central persistent storage layer for telemetry events.

The stored information can subsequently be used by different SEWAC components for:

- Citizen collection information
- Waste analytics
- Vehicle monitoring
- Driver monitoring
- Collection tracking
- Operational dashboards
- Reports
- Error investigation
- Historical analysis

These operations are handled outside the static Prisma model.
